# services/ops — фоновые задачи TMGoods

Python-сервис рядом с сайтом на Next.js. Ходит в ту же базу Supabase, но своей ролью
`ops_service` с минимумом прав (миграции `supabase/migrations/0007`, `0008`): владеет только
схемой `ops`, читает `parts`, `kits` и `site_orders` без данных покупателей.

Стек: Python 3.12, SQLAlchemy 2.0 (async, psycopg 3), Alembic (только схема `ops`), FastAPI,
Celery + RabbitMQ, prometheus-client, pytest.

## Что делает

| Задача | Когда (МСК) | Где выполняется |
|---|---|---|
| `export_orders` — заказы за вчера в CSV | 03:00 | очередь на Postgres |
| `market_feed` — фид Яндекс.Маркета (YML) | 05:00 | ставит Postgres, считает Celery |
| `procurement` — что дозаказать, с раскрытием комплектов | 06:00 | очередь на Postgres |
| `daily_summary` — продажи за вчера в Telegram | 09:00 | очередь на Postgres |

Фид отдаёт сайт: https://tmgoods.ru/feeds/yandex-market.yml

## Две очереди и почему обе

**Очередь на Postgres** (`ops/queue.py`) — главная. Захват `FOR UPDATE SKIP LOCKED`, приоритеты,
срок годности задачи, повторы с растущей паузой, ключ идемпотентности, журнал попыток `ops.job_runs`,
возврат задач умершего воркера. Плюсы: нет лишнего сервиса, задача и её результат лежат в той же
базе, что и данные, — постановку можно сделать в одной транзакции с изменением данных; история
и разбор ошибок — обычный SQL. Минусы: каждый захват — запрос к базе, поэтому на тысячах задач
в секунду она упрётся в базу; нет готовых примитивов «разложить на части и собрать».

**Celery + RabbitMQ** (`ops/celery_app.py`, `ops/feed.py`) — для работы, которую выгодно
распараллелить. Фид собирается chord-ом: 12 частей по типам товаров параллельно (group),
затем сборка файла, которая ждёт все части. Подтверждение после выполнения (`acks_late`):
если воркер упал посреди части, RabbitMQ отдаст её другому. Плюсы: брокер держит большой
поток сообщений без нагрузки на базу, готовые group/chord/chain, ограничения скорости,
масштабирование числом воркеров. Минусы: ещё два сервиса (≈250 МБ памяти на маленьком сервере),
chord требует общего хранилища результатов — здесь это та же база (`ops.celery_taskmeta`),
со встроенным `rpc` он не работает.

**Как они связаны.** Задачу `market_feed` ставит очередь на Postgres по расписанию и ждёт результат
Celery до 4 минут. Если Celery или RabbitMQ лежат, задача уходит на повтор, а после последней
попытки — в `dead`, и Grafana присылает тревогу в Telegram. Так у тяжёлой работы есть та же
история, повторы и оповещения, что у остальных задач.

## Мониторинг

Воркер отдаёт метрики на `:9108/metrics` (только внутренняя сеть docker). Prometheus, Grafana

## События заказов из Kafka

Витрина после оформления заказа публикует `order.created` в топик `orders` (`web/order-events.ts` — продюсер из Next.js-витрины,
идемпотентный продюсер kafkajs, ключ — id заказа). В событии только id, состав (артикул и количество)
и сумма: имени и телефона нет, ops они не нужны. Без `KAFKA_BROKERS` витрина ничего не отправляет,
сбой брокера оформление не роняет.

`python -m ops.events` читает топик группой `ops` (`ops/events.py`) и ставит пересчёт закупок:

- **Как минимум один раз + идемпотентность.** Смещение коммитится только после записи задачи в базу.
  Повторная доставка отсекается ключом задачи.
- **Окно 10 минут.** Ключ строится из времени события (`procurement:orders:<начало окна>`), задача
  стартует после конца окна. Повтор того же события попадает в то же окно; пачка заказов даёт один
  пересчёт. Живой прогон: 4 события → 1 задача, 3 склеены.
- **DLQ.** Событие не по схеме (не JSON, нет полей, время без пояса) уходит в `orders.dlq` с причиной
  в заголовке `error` и не блокирует партицию.
- Метрика `ops_events_total{result=queued|coalesced|ignored|dead_letter}`.

```bash
docker compose -f docker-compose.kafka.yml up -d      # брокер KRaft, только для разработки
KAFKA_BROKERS=localhost:9092 uv run python -m ops.events
```

Тесты (`tests/test_events.py`): разбор и отказ с причиной, окно в UTC, повторная доставка, сквозной
прогон через живой брокер — два события одного окна дают одну задачу, мусор лежит в DLQ, смещения
группы закоммичены за всеми сообщениями. Без брокера сквозной тест пропускается.

На боевом сервере Kafka не поднята: брокеру нужно 400+ МБ, а сервер на 3 ГБ уже занят сайтами.

## Аналитика продаж в ClickHouse

Задача `analytics_sync` (`ops/analytics.py`) переливает строки заказов из Postgres в ClickHouse
(`sales_lines`); отчёты — по месяцам и по позициям — считаются там.

- **ReplacingMergeTree(synced_at), ключ (order_id, line_no).** Выгрузка берёт окно последних дней
  целиком; повтор заменяет строки, а не дублирует. Смена статуса (отмена) доходит до отчёта при
  следующем прогоне. Слияние версий фоновое — отчёты читают с `FINAL`.
- Партиции по месяцам, `LowCardinality` для статуса, время в часовом поясе магазина.
- Тесты на живом ClickHouse (`CLICKHOUSE_TEST_URL`): повтор выгрузки не задваивает, отмена
  уменьшает выручку, заказ вне окна не попадает.

**Замер на 5 млн строк** (локально, один и тот же отчёт: выручка и число заказов по месяцам без отменённых):

| | Время запроса | Объём на диске |
|---|---|---|
| ClickHouse (MergeTree) | 0.06–0.12 с | 39.5 МБ |
| Postgres 16 (таблица без индексов) | 1.8–2.7 с | 352 МБ |

Сравнение честное в одну сторону: Postgres можно ускорить индексами и предагрегатами, но это
поддерживать руками на каждый новый отчёт. Колоночная база даёт такую скорость на любом срезе.
Для текущих 420 заказов разницы нет — ClickHouse нужен, когда история растёт в миллионы строк.

```bash
docker compose -f docker-compose.analytics.yml up -d   # ключи — .env.analytics (образец .env.analytics.example)
CLICKHOUSE_URL=http://user:pass@localhost:8123/tmgoods
```

## gRPC рядом с REST

`python -m ops.grpc_server` — сервис `Ops` на :50051 (`proto/ops_rpc.proto`), те же операции, что у REST
(`ops/api.py`), плюс стрим:

| Метод | Что делает |
|---|---|
| `EnqueueJob` | ставит задачу; с `idempotency_key` повтор возвращает ту же задачу и `created=false` |
| `GetJob` | статус, попытки, результат, ошибка |
| `WatchJob` | **серверный стрим**: каждая смена статуса, закрывается сам на `done`/`dead`/`expired` |

- Ключ — metadata `x-ops-key`, проверяет перехватчик до вызова метода (и для стрима тоже).
  Без заданного `OPS_API_KEY` закрыто всё — как у REST.
- Ошибки — статусами gRPC: неизвестная задача и не-объект в payload → `INVALID_ARGUMENT`,
  нет задачи → `NOT_FOUND`, нет ключа → `UNAUTHENTICATED`.
- Зачем второй протокол: дашборду, который ставит выгрузку и ждёт результат, REST даёт только
  опрос `GET /jobs/{id}` по таймеру; `WatchJob` держит одно соединение и присылает изменения.
  Внутри сервер пока опрашивает базу раз в 0.5 с; следующий шаг — `LISTEN/NOTIFY` Postgres.
- Код из proto генерируется `sh proto/generate.sh` и лежит в `ops/rpc/`.

## Запуск и проверка

```sh
uv sync
docker run -d --name ops-test-db -e POSTGRES_PASSWORD=test -e POSTGRES_DB=ops_test \
  -p 127.0.0.1:5434:5432 postgres:16
uv run pytest            # тесты ходят только в локальную базу, Celery в них синхронный
```

Тесты: 8 воркеров разбирают 200 задач без дублей; повторы, dead, таймаут, зависшие задачи,
сроки, расписание; расчёт закупок совпадает с TypeScript-оригиналом (`lib/analytics/procurement.ts`)
на демо-данных; фид — валидный YML с экранированием; метрики отражают состояние очереди.

На сервере всё поднимает `docker compose` из корня: `ops-worker` (при старте `alembic upgrade head`),
`celery-worker`, `rabbitmq`. Секреты — `.env` и `rabbitmq.env` рядом (в git не попадают).
